# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A local WordPress install for the site **osteza.es**, run through Docker Compose. The project root *is* the WordPress document root: it is bind-mounted to `/var/www/html` in the `wordpress` container, so edits to files here are live immediately, with no build step.

The active theme is the custom classic PHP theme `wp-content/themes/osteza/`. Pages are composed in the block editor from the theme's own section blocks; projects and the blog (archive, category, search, article) are PHP templates. Polylang is the only active plugin. There are no tests, no linter, and no Composer/npm setup.

## Commands

```sh
docker compose up -d      # start (site at http://localhost:8080, port set by WP_PORT in .env)
docker compose stop       # stop, keeping the database
docker compose logs -f wordpress   # Apache/PHP logs
```

`docker compose down -v` deletes the `db_data` volume and with it all site content and settings — do not run it without asking.

WP-CLI is **not** installed in the `wordpress:php8.3-apache` image. To inspect or change database state, query MySQL directly:

```sh
docker compose exec -T db sh -c 'MYSQL_PWD=$MYSQL_PASSWORD mysql -u$MYSQL_USER $MYSQL_DATABASE -e "SELECT option_name, option_value FROM wp_options WHERE option_name IN (\"template\",\"active_plugins\")"'
```

To run PHP inside WordPress context: `docker compose exec -T wordpress php -r 'require "wp-load.php"; ...'`.

## Layout and what to edit

- `wp-admin/`, `wp-includes/`, and the root `wp-*.php` files are WordPress core (7.1.x). Never edit them; core updates overwrite them. The same goes for bundled themes (`twentytwenty*`) and third-party plugins (`polylang`, `akismet`).
- Custom work belongs in `wp-content/themes/osteza/` (or a new plugin under `wp-content/plugins/`).
- `wp-config.php` is generated by the container on first run and is gitignored. It reads everything from `WORDPRESS_*` environment variables (via `getenv_docker`), so change configuration in `compose.yaml` / `.env`, not in the file. For example, debug mode is `WORDPRESS_DEBUG: 1` in the `wordpress` service environment; extra `define()`s go in `WORDPRESS_CONFIG_EXTRA`.
- `.env` holds the local DB credentials and `WP_PORT`; it is gitignored along with `wp-content/uploads/` and `wp-content/cache/`.
- `.htaccess` is written by WordPress (pretty permalinks, `/%postname%/`); the block between the `BEGIN/END WordPress` markers is regenerated automatically.
- The design sources are HTML files in the project root, not part of WordPress. `OSTEZA — Web*.html` are self-unpacking bundles (open in a browser) with desktop and mobile artboards; each newer one is a superset of the older, and `OSTEZA — Web - про нас.html` has home, service, blog archive, article, services catalogue, contact and about. The other `*.html` files are plain single-page designs: `zonas.html` and `zona-altea.html` (zones index, zone page), `proyectos.html` and `proyectos-con-proyectos.html` (projects archive, empty and with projects), `proyecto-caso.html` (project case study), `404.html` (not-found page, implemented in `404.php`). The design runtime wraps interpolated text in an extra `<span>`, so a few texts render smaller in the bundles than their own CSS specifies; the theme follows the CSS.

## The `osteza` theme

- **Every page is built from OSTEZA blocks** (block editor, category "OSTEZA"). `inc/blocks.php` defines each section once: its fields (type, label, default) become block attributes, and `blocks/<name>.php` renders it with the attributes in `$a`. The editor script `assets/js/blocks.js` (no build step) is generic: it shows a server-side preview of the section in the canvas and builds the sidebar form from the field definitions, so a new field only needs adding in `inc/blocks.php` and using in the render file. Field types are listed at the top of `inc/blocks.php` (`html` fields accept `<span>` highlights and the tokens `{contacto}` / `{privacidad}`; `lines` is one item per line; `page`/`link`/`zone`/`group` store ids, resolved to the current language when rendering). `prose` is the only block with inner blocks (normal paragraphs, headings, lists), used by the legal pages.
- Page templates (`page-templates/*.php`, `page.php`, `front-page.php`) only call `osteza_the_sections( $type )`: the page's blocks, or, while its content is empty, the default sections of `osteza_layout( $type )` in `inc/layouts.php` (home, services, service, zones, zone, contact, about). The layouts double as the starting content of new pages: `osteza_serialize_layout()` turns one into block markup. The templates still matter: helpers find the catalogue, contact, about, zones and blog pages by template (`osteza_template_page_url()`), and the template sets the page type.
- The home page is the static front page "Inicio" (Settings → Reading), with translations "Home", "Головна", "Главная", "Strona główna" holding a copy of the Spanish sections to translate. Polylang's `redirect_lang` option is on, so each language's front page is served at `/en/`, `/uk/`… (after changing that option, Polylang's languages cache needs `PLL()->model->clean_languages_cache()`).
- Content model (`inc/data.php`): **services are pages** with the "Servicio" template under "Servicios". Their card (text, tags, icon from `inc/icons.php`, colour, optional photo shown at the top of the home carousel card; a translation without its own photo uses the Spanish page's), group, "show on home" and "hide from menu" are in the "Tarjeta del servicio" box of the page editor; the name is the page title and the order is the page order. Groups are the taxonomy `osteza_group` (Páginas → Grupos de servicios: name, description = catalogue intro, "Orden"; slugs `montaje`, `transporte`, `coordinacion`, `reformas`, `acabados`, translatable with Polylang). From these come `osteza_all_services()`, `osteza_services()` (home cards, footer, mobile menu, contact form options, zone pages), `osteza_catalog()`, `osteza_service_menu()` (mega menu). **Zones are pages** with the "Zona" template under "Zonas"; comarca, coverage, coordinates and fallback-map position are in the "Datos de la zona" box; `osteza_zones()` feeds the map, lists and footer. Lists read the default-language pages and link to their translation (`#` while untranslated).
- The business focus is kitchen and furniture assembly, then moving and transport (based in Benidorm, all of Spain and Europe), then finding professionals (`coordinacion`: either 2–3 vetted professionals for the client to pick, for a commission, or full management where OSTEZA hires and pays them); renovations and finishes are secondary. That order is the group order and the page order.
- Projects (`inc/projects.php`): custom post type `osteza_project`, archive `/proyectos/`, case study `single-osteza_project.php`, edited in the "Datos del proyecto" box. Its services are default-language service page ids (`osteza_p_services`); its filter group is a group slug. Six template projects are drafts flagged `osteza_sample`. After changing the post type's rewrite settings, flush rewrite rules.
- Shared texts outside pages: contact details and the footer/mega-menu texts are theme mods in Appearance → Customize ("OSTEZA — Contacto", "OSTEZA — Textos generales"); the texts are registered as Polylang strings (Languages → Translations). Footer legal links are the pages "Aviso legal", the privacy policy page and "Política de cookies"; they are drafts until the owner registers as autónomo, and while the privacy page is unpublished `osteza_html()` drops the sentence linking to `{privacidad}` and the contact form omits its link.
- Favicons, the Apple touch icon and the web manifest are static files in `assets/img/icons/`, printed in `wp_head` by `functions.php` unless a site icon is set in the Customizer. Sections can be hidden without deleting them through core block visibility (`metadata.blockVisibility: false`); the about page's team block is hidden this way until there are real profiles.
- `osteza_anchor( 'contacto' )` is the target of every "Solicitar presupuesto" button: `#contacto` on pages with a contact block, otherwise the contact page's form. Leaflet (vendored in `assets/vendor/leaflet/`) is enqueued only on pages with the `zones-head` or `area` block.
- The blog uses native posts and categories; all logic is in `inc/blog.php`.
  - The archive is the page with the template `page-templates/blog.php` ("Blog", slug `blog`); `category.php` and `search.php` render the same layout (`template-parts/blog/archive.php`) from the main query, which `pre_get_posts` restricts to posts, 9 per page. `osteza_blog_url()` finds the blog page by its template.
  - The featured article is the newest sticky post. It is shown apart on page 1 of the blog and of its own category, and excluded from those lists.
  - Covers are graphics, not images: text, colour and icon come from the post meta `osteza_cover_text|color|icon`, edited in the "Portada del artículo" box of the post editor. The meta `osteza_sample` marks example copy, which the theme labels "Borrador". The articles are real copy now (none is flagged); the author's per-language bio is the user meta `description` / `description_<lang>` (Polylang).
  - `single.php` builds the table of contents from the `<h2>`s of the content (`osteza_article()` adds the ids). Inside article content these classes are styled, set through a block's "Additional CSS class": `chk` on a list (checklist), `callout` and `sumbox` on a group. The shortcode `[osteza_cta title="" text=""]` inserts the inline call to action.
  - `template-parts/blog/card.php` is the post card used by the archive, the article's "Sigue leyendo" and the home page; `template-parts/cta.php` is the dark call-to-action band.
- `assets/css/main.css` has three parts: self-hosted fonts (Onest, Unbounded), the design's stylesheet copied verbatim (short class names such as `.os`, `.dk`, `.wrap`, `.sec`, `.kick`, `.disp`, `.btn-*`), then the service page's design styles, then component classes that replace the design's inline styles. Later rules override the verbatim block, so when adding a class that sets `display`, check the design's `max-width:760px` / `1100px` media queries.
- A page whose first block is `hero` gets the body class `hdr-over` (`inc/blocks.php`): the sticky header is transparent with white content (light logo) over the hero, and turns solid once `main.js` adds `.on` on scroll or a header menu is open.
- JavaScript is written in ES6+ (no build step). `assets/js/main.js` is dependency-free and driven by `data-*` attributes (header shadow, mega menu and language dropdown, mobile menu, services carousel, contact form). Its translatable strings come from `wp_localize_script` in `functions.php` as `window.OSTEZA`.
- The contact form sends nothing to the server: it validates, builds a message and hands it to WhatsApp (`wa.me` link) or Telegram (copy and paste).
- Live chat (`inc/chat.php`, `template-parts/chat.php`, the chat block of `main.js`): an OpenAI model answers visitors through the REST route `osteza/v1/chat` (raw `wp_remote_post` to the Responses API with `store: false`, no SDK) and asks where the job is. Its tool `show_request_form` (or the visitor's "talk to a person" button) opens a request form in the chat, prefilled from the conversation: name, phone, town or address (optional browser geolocation), where to answer (WhatsApp, Telegram or a call), the request and up to 5 photos, resized in the browser. `osteza/v1/chat/request` sends it with the photos to the team's Telegram through the bot, with a `wa.me` / `t.me` / `tel:` link to answer; the team then replies in that channel (the bot does not relay replies). Conversations are private posts `osteza_chat` (wp-admin → Chats, with Chats → Ajustes for setup); `_oc_log` is what the visitor sees, `_oc_api` the input items replayed to the model (output items kept as returned), `_oc_lead` the request. Secrets are env vars passed in `compose.yaml` from `.env` (`OSTEZA_OPENAI_KEY`, `OSTEZA_TG_TOKEN`, optional `OSTEZA_TG_CHAT`, `OSTEZA_CHAT_MODEL`, default `gpt-6.1-sol`); without the API key the chat is not shown. Limits (`osteza_chat_enabled()` hides the chat when any money limit is hit): a monthly budget in dollars, at most a fifth of it per day, computed from each response's `usage` and per-million-token prices (option `osteza_chat_limits`, edited in Chats → Ajustes; spending in `osteza_chat_spend`); a 401 or `insufficient_quota` from OpenAI pauses the chat for the month (`osteza_chat_paused`, cleared there with «Reanudar»). Per-IP message and request limits and a daily request cap are transients (`osteza_chat_count()`); the daily cron `osteza_chat_cleanup` deletes conversations without a request after 180 days and with one after 730.
- Phone, WhatsApp, Telegram, email, address, hours, social URLs and legal holder are theme mods edited in Appearance → Customize → "OSTEZA — Contacto" (`inc/customizer.php`). While one is empty, `osteza_contact()` prints the design's bracketed placeholder such as `[TELÉFONO]`.
- Source strings are Spanish, wrapped in gettext with the `osteza` text domain. `languages/osteza.pot` is extracted with `xgettext` (keywords `__`, `_e`, `esc_html__`, `esc_html_e`, `esc_attr__`, `esc_attr_e`, `_x:1,2c`, `_n:1,2`), and `languages/<locale>.po/.mo` exist for `en_US`, `uk`, `ru_RU`, `pl_PL` (compile with `msgfmt`). These cover the theme's own interface and the block editor labels; page content is translated per language in the pages themselves. Bracketed texts like `[Presentación real del equipo…]` are content placeholders awaiting real copy; in the translations they read `[CONFIRM]`, `[УТОЧНИТИ]`, `[УТОЧНИТЬ]`, `[DO POTWIERDZENIA]`.
- Every Spanish page, post, category and service group has en/uk/ru/pl translations linked in Polylang (the six template projects, being drafts, do not). Block attributes that point to pages store the Spanish page id and resolve to the current language when rendering, so a translated page keeps working links. Translated pages need their own slugs: Polylang (free) does not share slugs across languages, and top-level slugs must not clash with another language's (e.g. pl services is `oferta`, ru zones `goroda`).
- Palette (after the logo): dark sections and text deep indigo `#1D1838`, accent violet `#5B3A92`, highlights on dark rose `#EBA3AE`, light background `#F8F5F3`; the home hero has an indigo→violet→sunset gradient.

## State lives in the database, not in files

Much of what defines the site is stored in MySQL (the `db_data` Docker volume), not in this directory: active theme and plugins, pages, navigation, Site Editor customisations (`wp_global_styles`, `wp_navigation`, template overrides), and all Polylang configuration. A change made in wp-admin will not show up as a file diff, and a file-only checkout does not reproduce the site. Anything that must be reproducible should be expressed in theme/plugin code (`theme.json`, templates, patterns, PHP).

## Multilingual

The site is multilingual via Polylang (free), with five languages configured: `es` (Castellano), `en`, `uk`, `ru`, `pl`. The WordPress admin locale is Ukrainian (`WPLANG=uk`; core translations are in `wp-content/languages/`). Any user-facing string in custom theme/plugin code must be translatable (`__()`, `_e()`, etc. with a text domain) and content must be considered per language — pages, menus, and Polylang-registered strings exist once per language.

The README and project communication are in Ukrainian.
