# Аудит безпеки OSTEZA

Дата завершення: 22.10.2026. Перевірено локальний WordPress у Docker. Робочий хостинг, DNS, TLS, WAF і зовнішні облікові записи до цього аудиту не входять. Експлуатацію відомої вразливості Polylang не запускали. Паролі, токени, реальні розмови й заявки не виводилися у звіт; реальних повідомлень та платних AI-запитів не надсилали.

## Виявлено й виправлено

| Пріоритет | Знахідка | Виправлення та перевірка |
|---|---|---|
| Високий | Встановлено Polylang 3.8.10; офіційний changelog містить виправлення десеріалізації недовірених даних у 3.8.11 | Оновлено офіційним WordPress upgrader до 3.9.1. Контрольні суми оновленого плагіна збігаються з WordPress.org. Всі 265 сторінок після оновлення проходять HTTP-перевірку |
| Середній | Токен історії чату передавався в GET URL і міг потрапляти до access logs | Клієнт передає його заголовком `X-OSTEZA-Token`. GET-токени в query не приймаються. POST body залишається сумісним зі старими клієнтами. Секрети не додаються до URL новим JS |
| Середній | Не було явної заборони кешування приватних відповідей чату | Для всіх відповідей chat REST, включно з помилками: `Cache-Control: private, no-store, max-age=0`, `Pragma: no-cache`, `X-Robots-Tag: noindex, nofollow`. У fetch також `cache: no-store` |
| Середній | Чати успадковували права стандартних записів: редактор міг отримати доступ до приватних розмов | Читання, редагування й видалення чатів потребують `manage_options`; тести підтвердили заборону для редактора та доступ адміністратора. Поточна база має одного адміністратора; доказу доступу сторонньої особи немає |
| Середній | Порожній збережений токен міг пройти порівняння з порожнім вхідним значенням; некоректний токен існуючої розмови трактувався як початок нової | Обидва токени мають бути непорожніми 32-байтовими рядками, порівнюються через `hash_equals`. Невірний токен існуючого id повертає 404. Перевірено на одноразових тестових записах |
| Середній | Публічні POST приймали запити з інших сайтів; не було схем типів і розмірів REST-параметрів | Перевіряються `Origin` і `Sec-Fetch-Site`. Додано REST-схеми: типи, довжини рядків, невід’ємні id/after, дозволені канали. Некоректні масиви повертають 400 до звернення до провайдерів |
| Середній | Після ліміту AI-ходів нові повідомлення все одно додавалися в історію; не було глобальної межі створення чатів | Після 40 повідомлень історія більше не збільшується, залишається форма заявки. Створення нових розмов обмежено 300 на день для всього сайту. Вже наявні IP-ліміти та блокування платних запитів збережено |
| Посилення | Некоректна вкладена структура upload-масивів могла спричиняти TypeError | Перевіряються масиви, типи шляхів, upload error, реальне HTTP-завантаження, MIME, кількість і розмір. Довільний локальний шлях не можна видати за завантажений файл |
| Посилення | Редактор PHP-файлів адміністративної панелі був увімкнений; pingback-методи залишалися доступними | MU-плагін вмикає `DISALLOW_FILE_EDIT`, прибирає pingback-методи XML-RPC. Оновлення WordPress і плагінів не вимикаються |
| Посилення | Не було окремих заборон HTTP-доступу до wp-config і виконуваних файлів uploads | Apache повертає 403 для `wp-config.php` та шляхів PHP/PHTML/PHAR у uploads. Раніше доданий захист `.env`, `.git`, службових файлів і директорій перевірено повторно |
| Посилення | `.env` мав локальні права 0644 | Обмежено до 0600. Файл не відстежується Git, історії цього шляху в Git немає. Збережені ключі не змінювалися |
| Посилення | Не було базових захисних HTTP-заголовків | Додано й перевірено `nosniff`, `SAMEORIGIN`, `strict-origin-when-cross-origin`, Permissions-Policy без камери/мікрофона, з геолокацією лише свого origin |

Перевірка Origin захищає від небажаних браузерних запитів з інших сайтів, але не є автентифікацією ботів: прямий HTTP-клієнт може не передавати ці заголовки. Rate limits за `REMOTE_ADDR` потребують правильної конфігурації проксі на робочому хостингу. Довільні `X-Forwarded-For` у застосунку не вважаються довіреними.

## Контроль цілісності й конфігурації

Порівняно з офіційними WordPress.org checksums після оновлення:

- WordPress 7.1.3: 3337 файлів;
- Polylang 3.9.1: 544 файли;
- AI Provider for OpenAI 1.2.0: 11 файлів;
- AI Provider for Anthropic 1.0.5: 12 файлів.

У цих **3904 перевірених файлах** немає розбіжностей чи відсутніх файлів. Це перевірка відповідності upstream, а не гарантія відсутності всіх можливих вразливостей або сторонніх файлів.

Додатково: PHP 8.3.35; реєстрація користувачів вимкнена; `WP_DEBUG=false`, ефективне `display_errors` вимкнене; AUTH_KEY не містить стандартної заглушки. Поточних адміністраторів: один. У власному коді теми, MU-плагіна, scripts/tests не знайдено ключів за перевіреними шаблонами провайдерів. У uploads не знайдено PHP/PHTML/PHAR-файлів, у власному коді немає world-writable файлів. Це не перевірка складності пароля адміністратора.

## Тести

- `docker compose exec -T wordpress php tests/security.php` — 20 успішних перевірок: ізоляція розмов, відмова порожнім і чужим токенам, GET query-token, Origin, REST-типи/довжини, вкладення, обмеження історії, права ролей, file editor і pingback.
- `docker compose exec -T wordpress php tests/launch-readiness.php` — 20 успішних перевірок доставки фото, повторів, блокувань MySQL, лічильників, бюджету й SEO; зовнішній HTTP перехоплюється.
- `python3 tests/check-http.py` — службові файли та виконувані uploads повертають 403; приватна REST-помилка має no-store; захисні заголовки присутні; перевірки SEO п’яти мов і 404 пройшли.
- Повторний crawl 265 сторінок і статей: немає HTTP/PHP-помилок, відсутніх описів, проблем із H1 або локальними якорями.
- PHP lint, JS syntax check і `git diff --check` пройшли для внесених змін.

Резервування перед оновленням: `/private/tmp/osteza-backups/osteza-20261021T203610Z.sql`, відповідний архів uploads та `polylang-3.8.10-before-security-update.tar.gz`. Не використовуйте `/private/tmp` як постійне сховище резервних копій.

## Що залишається до запуску

1. Увімкнути **2FA для адміністратора**. Налаштування другого фактора потребує участі власника; у цьому аудиті його не налаштовували.
2. На хостингу налаштувати **HTTPS**, захист входу від перебору, WAF/rate limits для login/XML-RPC і chat REST, та правильну передачу реальної IP від довіреного проксі. Локальний HTTP на loopback не є перевіркою production TLS.
3. Налаштувати автоматичні зовнішні резервні копії й графік перевірки оновлень. Поточні ручні копії не замінюють цю систему.
4. Перевірити права власності на production. Локальний `wp-config.php` залишається доступним на читання PHP-процесу через Docker bind mount і закритий по HTTP; на хостингу потрібні мінімальні права читання з урахуванням власника/групи.
5. Привести resource limits PHP/вебсервера у відповідність до фото: локально `upload_max_filesize=2M`, `post_max_size=8M`, а максимальний прикладний ліміт фото — 10 MB. Браузер зменшує фото, але серверні ліміти все одно визначають фактичне приймання. Не підвищувати їх без контролю загального розміру запиту.
6. Для нових CSP/антибот-рішень потрібна окрема перевірка сумісності з редактором WordPress, мапою й чатом. Повний CSP і CAPTCHA не додавалися довільно.

| Знахідка | Виправлення |

Архіви авторів і `?author=N` переадресовують на головну. Users REST доступний лише після входу (редактор блоків працює). Users sitemap вимкнено, з oEmbed прибрано автора |

| Розкриття версій: `readme.html`, `license.txt`, `<meta name="generator">`, `X-Powered-By` | Файли повертають 403, generator прибрано зі сторінок і фідів, `X-Powered-By` прибрано |
| Не було HSTS і CSP | HSTS (1 рік, без `includeSubDomains`) лише через HTTPS. CSP із безпечних директив: `frame-ancestors 'self'; base-uri 'self'; object-src 'none'` |

Копія БД перед змінами: `/private/tmp/osteza-backups/osteza-20261027T152339Z-before-security2.sql`. `tests/security.php` (29 перевірок) і `tests/check-http.py` розширено й пройдено.

Лишається на хостингу: 2FA, передача реальної IP від проксі (інакше блокування входу й ліміти чату спільні для всіх), `ServerTokens Prod` / `expose_php=Off` (заголовок `Server` в `.htaccess` не змінити), правила для Nginx, якщо хостинг не на Apache.
